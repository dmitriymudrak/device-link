# DeviceLink

Прототип ланцюжка «дрон → наземна станція → бекенд → оператор» на .NET. Симулятор дрона шле телеметрію бінарними кадрами по TCP. Наземна станція розбирає їх без алокацій, пересилає на бекенд через gRPC і по тому самому з'єднанню шле дрону команди. Десктопний клієнт показує всіх дронів на карті.

## Що вміє

- **Дрон (симулятор)** летить маршрутом і раз на секунду шле координати. Виконує команди станції: зависнути, продовжити, знищитися.
- **Наземна станція** (десктоп або консоль) приймає дрона, показує його стан і координати, керує ним кнопками, пересилає телеметрію на бекенд. Без зв'язку з бекендом тримає останні 10 с і досилає їх після відновлення.
- **Бекенд (Api)** приймає потоки телеметрії від багатьох станцій і роздає їх підписникам.
- **Viewer** (десктоп з картою або консоль) показує всі станції: маркер кожного дрона, а для вибраної станції — слід руху.

## Швидкий старт

Потрібен [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0).

```bash
# Windows (PowerShell)
./run.ps1

# Linux / macOS
./run.sh
```

Скрипт збирає рішення і запускає Api, десктопну станцію, симулятор і десктопний Viewer. Відкриються два вікна:

- **станція:** «Дрон: на зв'язку», координати, кнопки «Зависнути», «Продовжити», «Знищити»;
- **Viewer:** карта Києва з маркером дрона; клік на станцію в списку зліва показує її слід.

Закриття будь-якого з вікон або `Ctrl+C` зупиняє все.

Без вікон (Api, консольна станція, симулятор): `./run-services.ps1`.

Запуск частин вручну:

```bash
dotnet run --project src/DeviceLink.Api                      # http://localhost:5100
dotnet run --project src/DeviceLink.GroundStation.Desktop    # станція з вікном, порт 5000
dotnet run --project src/DeviceLink.GroundStation.Runner     # або консольна: [порт] [адреса Api] [id станції]
dotnet run --project src/DeviceLink.Simulator                # [хост] [порт], за замовчуванням 127.0.0.1 5000
dotnet run --project src/DeviceLink.Viewer.Desktop           # карта
dotnet run --project src/DeviceLink.Viewer                   # або консоль: [адреса Api] [id станції]
dotnet test
```

На одному порту може працювати лише одна станція: десктопна і консольна одночасно — на різних портах.

## Архітектура

```
                 Оператор у полі
                 (десктоп або консоль)
                        │ команди
Дрон ◄──TCP──► Наземна станція ──gRPC──► Api ◄──gRPC── Viewer
     бінарні кадри              HTTP/2           HTTP/2   (карта)
     в обидва боки
```

- **Дрон ↔ станція:** один дрон на станцію, одне TCP-з'єднання, дані йдуть ним в обидва боки: телеметрія від дрона, команди від станції. Дрон підключається сам і повторює спробу, доки станція не з'явиться. У реальній системі тут радіо або serial; TCP його замінює, кадри ті самі.
- **Станція → Api:** багато станцій, один бекенд; кожна має свій `stationId`. Керування дроном — лише локально зі станції.
- **Api → Viewer:** Viewer підписується на всі станції або на одну.

Логіка станції живе в бібліотеці `DeviceLink.GroundStation`. Десктопна і консольна станції — лише обгортки над нею.

## Протокол дрон ↔ станція

Усі числа big-endian.

| Поле | Байтів | Зміст |
|---|---|---|
| Marker | 2 | `AA 55` |
| Length | 2 | довжина payload, максимум 1024 |
| Type | 1 | тип повідомлення |
| Seq | 1 | лічильник відправника, по колу 255 → 0; у кожного напрямку свій |
| Payload | N | поля повідомлення |
| CRC16 | 2 | CRC-16/CCITT-FALSE (IBM-3740): poly `0x1021`, init `0xFFFF`, по Length + Type + Seq + Payload |

| Повідомлення | Type | Напрямок | Payload |
|---|---|---|---|
| Telemetry | `0x01` | дрон → станція | lat `i32`, lon `i32` (градуси × 10⁷) |
| Command | `0x10` | станція → дрон | commandId `u16`, code `u8`, arg `i16` |
| Ack | `0x11` | дрон → станція | заплановано |

Коди команд: `0x01` Hold — висіти на місці (телеметрія йде, координати не змінюються), `0x02` Resume — продовжити маршрут, `0x03` Destroy — дрон завершує роботу. Невідомий код дрон пропускає.

Приклад телеметрії — 50.4501, 30.5234 (Київ), seq 0:

```
AA 55        маркер
00 08        довжина = 8
01           тип = Telemetry
00           seq = 0
1E 12 13 08  lat = 504 501 000 → 50.4501
12 31 80 50  lon = 305 234 000 → 30.5234
2E 71        CRC16
```

Приклад команди — №1, Destroy:

```
AA 55 00 05 10 00 | 00 01 03 00 00 | 48 53
```

Очікувані байти й CRC у тестах узяті з незалежних джерел (crccalc.com, окремий скрипт), а не пораховані кодом, який тестується. Еталон CRC: `"123456789"` → `0x29B1`.

## Контракт gRPC

`src/DeviceLink.Api/Protos/devicelink.proto`, пакет `devicelink.v1`. Клієнти (станція, Viewer) підключають той самий файл з роллю `Client`.

| Метод | Тип | Хто викликає |
|---|---|---|
| `UploadTelemetry(stream TelemetryPoint) → UploadSummary` | client streaming | станція |
| `SubscribeTelemetry(SubscribeRequest) → stream TelemetryPoint` | server streaming | Viewer; порожній `station_id` = усі станції |

`TelemetryPoint`: `station_id`, `seq`, `lat_e7` і `lon_e7` (`sfixed32`), `received_at` — час, коли станція прийняла кадр.

## Рішення й компроміси

**Протокол**

| Рішення | Чому |
|---|---|
| Протокол — окрема бібліотека без мережі | нею користуються симулятор, станція й тести; парсер тестується масивом байтів; транспорт замінний (serial, UDP, TLS) |
| Маркер + довжина + CRC | довжина каже, скільки читати; маркер дає знайти наступний кадр після сміття; CRC відрізняє справжній кадр від випадкового `AA 55` у даних |
| Власний CRC16, хоч TCP має свою суму | сума TCP слабка й покриває лише дорогу між стеками; ті самі кадри підуть і по serial; CRC потрібен для ресинхронізації |
| Координати `i32` × 10⁷ | точність ~1 см у 4 байтах, однаково на всіх платформах; `float` дає похибку в метри; так робить MAVLink |
| Seq один байт по колу | показує пропуск між сусідніми кадрами, а не ідентифікує кадр |
| Ліміт payload 1024 | інакше зіпсована довжина `FF FF` змусила б парсер чекати 64 КБ і тримати пам'ять |
| `TryParse` без стану й без винятків | погані байти з мережі — норма; недочитаний хвіст зберігає `Pipe`; немає стану — немає чого зіпсувати |
| Ресинхронізація зсувом на 1 байт | довжині битого кадру вірити не можна; справжній кадр може починатися будь-де |
| Самотній `AA` у кінці буфера зберігається | TCP може розрізати потік між `AA` і `55`; викинути — мовчки втратити справний кадр |
| Payload — зріз, а не копія | нуль алокацій на кадр; ціна — читати одразу, за межі парсера виходять лише розібрані числа |
| `AdvanceTo(buffer.Start, buffer.End)` після циклу розбору | один `AdvanceTo` на одне читання; забираємо розібране, решту позначаємо переглянутою, щоб наступне читання чекало нових байтів |
| `IBufferWriter` у `Write`, payload через `stackalloc` | пишемо прямо в буфер отримувача; без масиву на кожен кадр |
| Невідомий тип кадру чи код команди пропускається | новий пристрій чи станція не ламають старі |

**Дрон і станція**

| Рішення | Чому |
|---|---|
| Двосторонній обмін по одному TCP-з'єднанню | TCP уже дуплексний: читання й запис незалежні; друге з'єднання — зайва складність і ще одна точка обриву |
| Один письменник на сокет: команди йдуть через `Channel` в одну задачу | кадри не перемішуються за конструкцією; немає `Release`, який можна забути; `lock` не працює з `await` |
| Своя черга команд на кожне з'єднання | команда без дрона повертає помилку, а не чекає і не знищує наступного підключеного дрона |
| Читання й запис зупиняються разом (`Task.WhenAny` + linked token) | обрив будь-якої половини закриває з'єднання цілком, і про це одразу видно |
| Hold шле останню точку, а не мовчить | дрон висить, але станція бачить, що він на зв'язку |
| `PeriodicTimer` у симуляторі | тікає за розкладом без дрейфу й не накладається, тож два кадри ніколи не пишуться в сокет одночасно |
| Дрон сам перепідключається до станції | порядок запуску неважливий; станція лише слухає, як у реальній системі |
| Один дрон — одне з'єднання, послідовний прийом | станція обслуговує рівно один дрон; після відключення чекає наступного |
| Обмежена черга (10, `DropOldest`) між читанням дрона і відправкою в Api | повільний чи недоступний Api не гальмує роботу з дроном; поки Api недоступний, черга і є буфером останніх 10 с |
| Мережа станції у фоні, оновлення вікна через `Dispatcher` | розбір кадрів не займає потік, що малює інтерфейс |

**Бекенд і Viewer**

| Рішення | Чому |
|---|---|
| Client streaming для станції, server streaming для Viewer | один довгий потік замість запиту на кожну точку; одразу видно, що станція на зв'язку |
| `TelemetryHub`: своя обмежена черга (100, `DropOldest`) на кожного підписника | повільний Viewer втрачає старі точки, а не гальмує станції й інших глядачів; пам'ять не росте |
| Хаб — singleton через DI, а не `static` | тестується, замінюється (наприклад, на брокер при кількох екземплярах Api), залежності явні |
| `.proto` у проєкті Api, клієнти посилаються на файл | один контракт; кожен генерує лише свою частину, клієнти не тягнуть ASP.NET Core |
| `sfixed32` для координат у protobuf | великі значення у varint займали б 5 байтів, від'ємні — 10; `sfixed32` завжди 4 |
| Карта — Mapsui з тайлами OpenStreetMap | безкоштовна й відкрита, з готовим контролом для Avalonia; свій User-Agent за правилами OSM |
| Слід лише для вибраної станції, до 300 точок | карта не захаращена; пам'ять обмежена; слід збирається для всіх, тож при виборі видно рух за останні хвилини |

## Відомі обмеження

- Дрон не підтверджує команди (Ack ще немає). Доставку гарантує TCP, поки з'єднання живе.
- «Тихо» мертве (напіввідкрите) з'єднання не помітно, доки не додано heartbeat.
- Без автентифікації й TLS.
- Хаб Api в пам'яті одного процесу: історії немає, Viewer бачить лише точки після підключення.
- При обриві зв'язку з Api губиться одна точка, яку саме відправляли.
- Маршрут інтерполюється лінійно в градусах — добре для кількох кілометрів, не для великих відстаней.
- Тайли OpenStreetMap — для демо; для продукту потрібен свій або платний сервер тайлів.

## Дорожня карта

1. **Надійність:** Ack і таймаут команд, Hello і Heartbeat з `TimeProvider`, reconnect з backoff і jitter, імітація збоїв у симуляторі, тест із випадковою нарізкою кадрів, метрики через `Meter`, CI.
2. **Доробки:** кілька станцій з одного вікна, маршрут дрона з координат, передача картинок шматками, версіонування протоколу, телеметрія по UDP, ArduPilot SITL, історія треку в базі.
